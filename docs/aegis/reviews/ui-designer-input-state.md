# UI 设计评审：桌面层窗口的四态可视契约

- **日期**：2026-10-22
- **评审角色**：UI 设计师（视觉系统 / 状态可判定性 / 无障碍）
- **触发问题**：窗口 SetParent 进 WorkerW 后「点不进去、打不了字」，界面上没有任何线索说明为什么
- **输入证据**：`src/app.rs`（wndproc 1069-1254、WM_SETFOCUS 1129-1133、WM_KILLFOCUS 1135-1140、WM_LBUTTONDOWN 1141-1153）、`src/render/theme.rs`、`src/render/painter.rs`（`draw_border` 345-355、`draw_overlay` 317-343）、`docs/design/2026-10-22-tlshell-ui-spec.md` §4.2 / §4.2.1 / §4.5
- **结论**：四态中只有「焦点态」被部分实现，且初始值在说谎；「提权态」完全没有实现，「告警态」语义与对比度都不合格，「失焦态」的视觉语言与规范冲突。**核心缺陷不是配色，而是「状态不可判定」**：窗口无法告诉用户它现在能不能接收键盘。
- **本文不改源码**，只定契约与偏差。

## 0. 三条必须先说清的前提

### P1 物理前提：整窗 alpha 让「常驻状态墨迹」无法成立

实现走 `SetLayeredWindowAttributes(..., LWA_ALPHA)`（`src/win/layered.rs:45`），即整窗统一 alpha；圆角是 `SetWindowRgn` 硬边裁剪（`src/win/layered.rs:94`）。

后果：**焦点描边、提权描边、`ADMIN` 字、告警条底全部与背景同比稀释**。`opacity = 0.30` 时，`#89b4fa` 在白壁纸上合成后约 **1.13:1**，在深壁纸上约 **1.9:1**——两种壁纸下都低于 3:1。也就是说，规范 §2.4 允许的 0.30 与规范 §1.3「焦点态必须可见」在当前架构下物理互斥。

因此本契约分两层：

| 层 | 要求 | 验收判定 |
|---|---|---|
| 契约本体 | 状态墨迹必须画在**不透明衬底**上（alpha 1.0），或迁移到逐像素 alpha | `opacity = 1.0` 时逐条量化 |
| 已知限制 K1 | `opacity < 1.0` 时状态墨迹同比稀释，焦点/提权线索可低于 3:1 | 记录，不视为回归；迁移逐像素 alpha 后删除本条 |

### P2 判定前提：契约必须「只看像素」就能判定

输入是否可用**没有**可信信号（无焦点就收不到 `WM_KEYDOWN`）。所以四态的每一条都必须能由「静态截图 + 2 帧时序」判定，**不得**依赖「打字有没有回显」。依赖回显的验收项（如 V-26）必须在无输入假设下重写，见 §6。

### P3 语义前提：三种线索不许互相借用

| 线索 | 表达 | 唯一含义 |
|---|---|---|
| 光标形态 | 实心块 / 空心框 | 焦点 |
| 描边色相 | 蓝（焦点）/ 黄（提权） | 有焦点 / 有管理员权限 |
| 文字条 | `未获得焦点…` / `以管理员权限运行…` | 可执行动作 / 身份事实 |

规矩：**焦点靠形态 + 蓝，提权靠常驻 + 黄，告警靠文字 + 位置**。任何一个通道都不得同时承担两种语义。

## 1. 四态正交模型

```
                  ┌─ C 提权层（常驻，正交，进程级） ─────────────┐
                  │  ring 2px 双色 + ADMIN chip               │
                  │  不随 A/B 变化，不随时间消失               │
                  └───────────────────────────────────────────┘
   A 焦点态 ⇄ B 失焦态        （WM_SETFOCUS / WM_KILLFOCUS 当帧切换，0ms）
        │
        └─ D 告警层（瞬时，正交，事件级）：
             阻塞型（焦点未获得 / 挂载降级 / 热键失败）→ 常驻到条件解除
             警告型 → 8s    提示型 → 3s
```

`A`、`B` 互斥；`C`、`D` 可分别叠加在 `A` 或 `B` 上，三层互不替代。同屏最多 `B + C + D` 三条线索同时存在，且必须仍可区分（判定见 §5）。

## 2. 四态契约（尺寸 / 颜色 / 动画 / 消失条件 / 对比度）

基准：`background #1e1e2e`、`foreground #cdd6f4`、`cursor #f5e0dc`、`elevated #f9e2af`、`focus_ring #89b4fa`；cell 8×17 @100% DPI（14px / 行高 1.25）；全部尺寸为物理像素，`DPI ≠ 100` 时按 cell 取整后同比缩放。

### 2.1 A 焦点态

| 项 | 规格 |
|---|---|
| 光标 | 实心块，整格 `8 × 17`；填充 `cursor #f5e0dc`；格内字符用 `background #1e1e2e` **反色重绘** |
| 闪烁 | 半周期 530ms（周期 1050ms）、占空比 50%；**获得焦点当帧必须为亮** |
| 描边 | 1px `#89b4fa`，**内描边**，距窗口边缘 inset 1px；沿圆角路径连续，四角不得断线 |
| 动画 | **0ms**。焦点是事实断言，淡入会把「能不能打字」变成猜测 |
| 消失 | `WM_KILLFOCUS` 当帧 |
| 对比度 | 描边 vs 有效底 `7.79:1`（≥3:1 通过）；反色字符 `12.95:1`；空心/实心形态差 ≥ 8 倍墨量 |

圆角处理：`stroke_rect` 只能画直角环（`src/render/painter.rs:62-74`）。在圆角 8 的窗口上，直角环会被 `SetWindowRgn` 硬边啃掉四角并露出断线——断线会被读成「描边坏了」，比不画更差。二选一：**画 7px 弧的圆角环**，或**把圆角降为 0**。不允许「直角环 + 被裁剪」。

### 2.2 B 失焦态

| 项 | 规格 |
|---|---|
| 光标 | 1px 空心矩形，边 `#f5e0dc`，整格 `8 × 17`，内部不填充、字符保持原色；**不闪** |
| 焦点描边 | **无**。失焦不得用任何蓝 |
| 边界基线 | 1px `background #1e1e2e` 不透明轮廓。语义是「窗口存在」，**不是**焦点。它保证在白壁纸上窗口可发现（`11.34:1`），是 §2.4「下限 0.30」能成立的前提 |
| 未就绪提示条 | 见 2.2.1 |
| 动画 | 进入 0ms；离开（获得焦点/鼠标离开）120ms 淡出 |
| 对比度 | 空心框 vs 底 `12.95:1`；边界基线 vs 白壁纸 `11.34:1` |

> **契约修订 R1**：规范 §4.2 写「无焦点：无描边」。实测该条无法与「低透明度下窗口可发现」共存。本契约改为：**无焦点=无焦点描边；保留一条与底同色的不透明基线**（视觉上不可见为线，只保证边界不被壁纸吞掉）。需回写 spec §4.2。

#### 2.2.1 未就绪提示条（B 态的门槛项）

| 项 | 规格 |
|---|---|
| 位置 | 窗口底部，占 1 行 `cell_h`，左右各缩进 `padding` |
| 尺寸 | 高 `17px`，宽 = 文本宽度 + 12（左右各 6 内边距），最大 `0.6 × client 宽` |
| 底色 | `#1e1e2e` **不透明** chip，圆角 4 |
| 文本 | `未获得焦点 · 点击窗口内任意位置开始输入`，14px，`#cdd6f4`，对比 `11.34:1` |
| 触发 | `!focused` **且** 鼠标位于窗内 |
| 消失 | 获得焦点当帧（120ms 淡出）；鼠标离开；窗口隐藏 |
| 动画 | 进入 0ms（同 A 的理由）；离开 120ms |

这是「点不进去」的唯一**事前**线索。当前实现里没有任何等价物。

### 2.3 C 提权态（正交，常驻）

| 项 | 规格 |
|---|---|
| 描边墨量 | 2px：外 1px `#1e1e2e` 不透明 + 内 1px `#f9e2af` |
| 有焦点 | 内圈保持 `#f9e2af` 满饱和，**不叠第二条线**，环宽不变 |
| 无焦点 | 同上，**不消失、不降饱和** |
| `ADMIN` 标注 | 右下角；caps 12px / 字重 600；文字 `#f9e2af`；不透底 chip `#1e1e2e`，内边距 4×2，圆角 2；距右 12、距下 12（与 padding 对齐）；宽约 44px |
| 动画 | **0ms**，进程生命周期内恒在 |
| 消失 | 仅进程退出（或未来实现降权重启） |
| 对比度 | 内圈 vs 底 `12.91:1`；外圈 vs 白壁纸 `11.34:1`；`ADMIN` 文字 vs chip `12.91:1`（≥4.5 通过） |

**为什么必须双色**：单色 `#f9e2af` 对白壁纸只有 `1.27:1`，单色 `#1e1e2e` 对黑壁纸只有 `1.0:1`。任何单色描边都不可能在任意壁纸上满足 3:1。双墨让「暗线保浅壁纸、亮线保深壁纸」，两条里总有一条成立。

### 2.4 D 告警态

| 项 | 规格 |
|---|---|
| 形态 | 单行 chip，右对齐，位于底部（与 `ADMIN` 冲突时上移一行） |
| 尺寸 | 高 `cell_h + 4` = `21px`；宽 ≤ `0.6 × client 宽`；内边距 6×2；圆角 4 |
| 底色 | `#1e1e2e` **不透明**；左侧 2px 严重度条 |
| 文字 | 14px `#cdd6f4`（`11.34:1`） |
| 严重度 | 阻塞 `#f9e2af` + 无前缀；错误 `#f38ba8` + 文本前缀 `error:`（不得只靠颜色编码，WCAG 1.4.1）；提示 `#89b4fa` |
| 动画 | 进 120ms 淡入 + 上移 2px；出 120ms；`SPI_GETCLIENTAREAANIMATION = 0` 时全部 0ms |
| 溢出 | 尾部省略号 `…`，完整文本进日志。**禁止静默截断** |
| 消失 | 按类别：阻塞型=条件解除或用户点条确认（**无 TTL**）；警告型=8s；提示型=3s；PTY 输出不冲刷阻塞/警告型 |

> **契约修订 R2**：规范 §4.5 写「PTY 有输出即消失」。这些告警恰恰出现在「用户正想输入、输出即将发生」的时刻，用输出清除会保证它们最短命。改为：冲刷权按严重度分配，见上。

> **契约修订 R3**：弃用 `selection #585b70` 作告警底（现状 `src/render/painter.rs:321`）。它 vs 底只有 `2.46:1`，文字 `4.62:1` 贴线，且与选区语义撞车（「这是我选的」vs「系统在说」）。

## 4. 「用户按了键但窗口没焦点」应给什么反馈

### 4.1 先承认约束

无焦点 ⇒ 收不到 `WM_KEYDOWN`/`WM_CHAR` ⇒ **事件驱动的反馈在原理上不可能**。任何「检测到按键后提示」的方案都必须先解决「怎么知道有按键」。所以反馈分三级，前两级不依赖按键探测。

### 4.2 L0 事前：把「现在不能打字」变成可看见的状态

即 2.2.1 的未就绪提示条 + 空心光标 + 无蓝框。判定方式：**只看一张静态截图**，不需要任何输入假设。这是唯一零依赖、零误报的层级，必须优先落地。

### 4.3 L1 失败当刻：点击后必须自检并当场报错

`WM_LBUTTONDOWN` 处理的正确顺序是「尝试取焦 → 校验 → 失败则可见化」：

1. 调用 `SetFocus(hwnd)`（子窗口必须用 `SetFocus`；跨进程宿主下需 `AttachThreadInput` 到宿主线程或先 `SetForegroundWindow(GetAncestor(hwnd, GA_ROOT))`）；
2. **校验** `GetFocus() == hwnd`；
3. 不等则进入 D 态阻塞告警：`未获得焦点 · 再点击一次`（或当前可用的最短动作句）。

价值：把「静默失败」变成「发生在用户意图最强那一秒的可见失败」。成本只有一次 `GetFocus()`。

### 4.4 L2 迟到发现：只在窄窗内做按键探测

若用户点过、仍无焦点、又继续敲键，可用现有能力探测：`GetAsyncKeyState` 已在 `src/app.rs:1272-1283` 用于修饰键，可复用。**必须窗限幅**，否则会在「鼠标停在终端上、人在别的窗口打字」时误报：

| 闸门 | 规则 | 理由 |
|---|---|---|
| 时间窗 | 仅在「最近 10s 内发生过一次焦点获取失败」后启用 | 语义是「对刚才那次点击的后续确认」，不是全局键盘监听 |
| 位置窗 | 仅在鼠标位于窗内时启用 | 与 L0 的 hover 条件一致 |
| 触发阈值 | 500ms 内 ≥2 个**不同** vk 的按下沿 | 单键可能是误触 |
| 误报预算 | 每次焦点失败最多升一级、最多报一次 | 不做持续提示 |
| 文案上限 | 一句动作句：「按键未送达 · 点击窗口内任意位置」 | 不出现 WorkerW / WS_CHILD / SetParent 等技术名词 |

安全边界：全局键盘监听不在本设计授权内，且与安全评审方向相反。上述轮询只在「用户刚刚点过这里」的窄窗内开启，建议与安全评审 S-13 一并签字（见 §7）。

### 4.5 无障碍出口

任何一条 L1/L2 告警必须同时走 `NotifyWinEvent(EVENT_SYSTEM_ALERT, hwnd, OBJID_CLIENT, 0)`（最低成本通道），否则读屏用户拿到的信息量为零。现状 D-15 为零暴露。

## 5. 同屏叠加的判定规则

`B + C + D` 同时存在时，必须仍能回答三个问题，且每个问题只由**一个**通道回答：

| 问题 | 唯一通道 | 判定方法 |
|---|---|---|
| 能打字吗？ | 光标形态（实心块 vs 空心） | 2 帧连拍，形态差 |
| 有管理员权限吗？ | 描边色相（黄）+ `ADMIN` 字 | 单帧取色，色相在 45–60° 区间 |
| 出什么事了？ | D 条文字（含 `error:` 前缀） | 单帧 OCR |

禁止的组合：黄框 + 蓝框同时出现（说明两条线叠了）；空心光标 + 闪烁（说明 `Blink` 没关）；`ADMIN` 与告警条重叠（说明层级没让位）。

## 7. 未决与需要签字的三件事

1. **焦点描边用色**：保留现状蓝 `#89b4fa`（7.79:1，与提权黄零冲突），还是回落到规范的无彩 `fg@24%`（1.88:1，**不达标**）？建议保留蓝并回写 spec §2.1/§4.2；若要无彩，最低 `fg@45%`（3.36:1）。
2. **L2 按键探测的授权边界**：`GetAsyncKeyState` 轮询在「刚点过 + 鼠标在窗内 + 10s 内」是否可接受？需安全评审 S-13 签字，否则 L2 整层不实现，只留 L0/L1。
3. **整窗 alpha → 逐像素 alpha 的时机**：不做则 K1 长期存在，`opacity < 0.72` 时焦点态与提权态都可能不可见（D-13）。建议在 M4 前决策，因为它是四态契约唯一的结构性阻碍。

---

## 8. 一句话总结

四态契约的本质不是四套颜色，而是**三个互不借用的通道各自回答一个二值问题**；当前实现把唯一能回答「能不能打字」的通道（光标 + 蓝框）在启动首帧就说成了「能」，而真正的失败（点击拿不到焦点）在界面上完全静默——这才是「点不进去」的产品级缺陷，比配色偏差严重得多。
